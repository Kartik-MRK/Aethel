One base model, versioned adapter experiments

Aethel is a version-control and provenance system for LoRA adapters. A frozen base model is identified by its model ID and immutable revision; each experiment produces adapter weights, configuration, and training/evaluation metadata. The adapter is versioned, while the base weights remain at their recorded source.

For standard LoRA, an update is represented by two low-rank matrices rather than a complete replacement weight matrix. Sizes depend on the model, rank, target modules, and saved classifier head. The two recorded DistilBERT experiments each have 2,667,272 bytes (about 2.54 MiB) of adapter weights. This is a measured example, not a universal adapter size.

A usable version is the adapter plus its configuration and pinned base reference. A reproducible evaluation also needs the original dataset, exact split, label meanings, and compatible runtime. Aethel records these relationships and checks their identities.

The complete workflow is initialize → train → evaluate → commit → compare → publish → clone/pull → verify provenance. The supported history is single-parent and fast-forward; merging is outside this command set. This handbook explains the implemented system and its operating limits.

Why content addressing and an external checkpoint serve different purposes

Local history is read from branch refs and immutable objects. A separate database is not required to resolve a local commit, so copying a complete .aethel/ repository preserves its history. Content addressing also deduplicates identical bytes and makes corruption detectable by rehashing.

A database is still useful for operational state: the provenance worker uses SQLite to remember mirror jobs and signed transactions. That does not make it a second authority for local version identity. The distinction is between authoritative artifact/history bytes and recoverable job state.

A correct hash proves that bytes match a stated identifier. A dishonest Hub can still advertise a different internally consistent history. An externally recorded checkpoint binds an ordered prefix to a trusted contract/log identity. A verifier with that independent identity can detect a rewritten prefix instead of merely asking the same server whether its answer is trustworthy.

A chain is not the only possible external witness. Aethel uses an EVM checkpoint to make the record independently inspectable. The public-testnet deployment demonstrates that workflow; its chain/provider assumptions remain part of the trust model.

Objects, branches, HEAD, and the workspace

.aethel/
  config.json                  schema version, pinned base, author, optional saved Hub URL/name
  HEAD                         ref: refs/heads/<branch>, or a detached commit digest
  refs/heads/<branch>           current commit digest; empty for an unborn branch
  objects/
    blobs/<ab>/<rest>          raw artifact bytes
    trees/<ab>/<rest>          filename-to-blob mapping
    commits/<ab>/<rest>        snapshot metadata and parent
    bases/<ab>/<rest>          model ID and immutable revision reference
  workspace/                   staged adapter artifacts

An object's path contains its SHA-256 digest, split after two hex characters. Two snapshots with identical weights share a blob but retain separate commit metadata. There is no database needed to reconstruct local history. A Hub has a separate object store plus repos.json, log.jsonl, anchors.jsonl, and worker state in provenance.sqlite3.

Local JSON writers use sorted keys, compact separators, UTF-8, and no NaN/Infinity. Hashing received objects uses their exact bytes, including whitespace; downloads must not parse and reserialize JSON before installation. Verified raw downloads preserve noncanonical JSON too.

A tree is a JSON mapping with a files field. Filenames must be nonempty single components; path separators, colons, NUL, . and .. are rejected. Extraction verifies all source blobs before replacement and verifies each copied file against its digest.

A schema-2 commit contains:

{
  "schema": 2,
  "parent_hash": null,
  "tree": "<tree digest>",
  "adapter_blob": "<adapter digest>",
  "base": "<base digest>",
  "message": "SST-2 baseline",
  "author": "Team member",
  "timestamp": "<ISO-8601 timestamp>",
  "training_info": {}
}

A parent is null or a valid digest. Tree, adapter, and base references must be valid and present. The adapter digest must agree with the preferred adapter entry in the tree: adapter_model.safetensors, then legacy adapter_model.bin. Safetensors is used for supported adapter comparison; arbitrary legacy pickle weights must not be treated as safe to load. Message, author, and timestamp fields are strings; training information is a mapping. Base objects record model_id and revision_sha, with schema/source metadata from local writers.

Refs are separate mutable files. Branch names reject path syntax, whitespace, hidden-name forms, trailing dots, lock suffixes, and reserved Windows names. Full hashes and unique short hashes can identify commits. Checking out a hash detaches HEAD; committing requires an attached branch. Schema 2 has one parent and does not implement merges.

Why a commit has its own content address

Two commits may contain identical adapter weights but differ in message, author, parent, or training metadata. If their metadata were stored under the adapter hash, both would share one metadata slot. The later write could silently replace the earlier version description.

Aethel instead hashes the commit object itself. Distinct metadata yields distinct commit addresses while both trees may reference the same weight blob. This avoids metadata collisions without making a full weight copy per commit. Integrity checks also enforce the redundant adapter_blob reference against the tree entry.

Durable writes, workspace rollback, and interrupted operations

Commit creation reads the staged adapter, verifies the base and evaluation bindings, stores blobs/tree/commit, and advances the branch last. The final ref write compares the expected branch and parent under the shared ref lock. Concurrent evaluation or ref changes cannot silently attach a commit to a different parent. Snapshotting does not clear the workspace.

Training and checkout build a replacement in a temporary directory. Under workspace.lock, the old workspace is hashed, the replacement is prepared, and the original is checked again before installation. The old directory becomes workspace.backup; installation or ref-write failure restores it. Pull uses the same mechanism with an exact clean-workspace requirement, including deleted files. Process termination can leave a backup/lock requiring inspection.

Object/ref writes use exclusive random temporary filenames on the destination filesystem, flush contents, atomically rename, and flush the parent directory where supported. Streamed copies hash the bytes actually copied before installation, preventing a source changing between the initial hash and copy from being stored under the wrong name.

fsck re-hashes stored objects, validates dependencies and the adapter/tree relationship, and checks reachability from branches and detached HEAD. Unreachable objects can result from an interrupted write; they are reported, not automatically deleted. Corruption needs a verified original copy. Verified writes and transfers can repair corrupt cached objects.

Installation, datasets, and a working experiment

python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev,hub,ml]'

The base installation works without torch or FastAPI for local versioning and Hub retrieval. [ml] adds training/evaluation/comparison; [hub] runs the server; [provenance] adds EVM verification. CUDA-only quantization dependencies live in the optional [gpu] extra.

For the supplied classification examples, download the demo datasets once:

python scripts/setup_demo_data.py

This helper downloads up to 800 rows from each of five public datasets into datasets/ at the checkout root. It overwrites those generated CSVs when rerun. The YAML examples in train_yaml reference those locations. Downloads require network access and the datasets package from [ml]. These small subsets are for workflow demonstrations.

For your own data, provide a CSV with text and numeric label columns and configure their names. The training YAML accepts a CSV path or a directory containing the expected training CSV. Use sst2_config.yaml as the starting configuration. Set task_type: sequence_classification, label meanings, LoRA rank/alpha, batch settings, seed, split_seed, and held-out fractions explicitly. Dataset paths resolve from the Aethel repository root; the --config path resolves from the command's working directory. Run the supplied examples from the checkout root.

Training and recording a version

aethel init --model distilbert/distilbert-base-uncased --author "Team member"
aethel train --config train_yaml/sst2_config.yaml
aethel eval --json
aethel commit -m "SST-2 baseline" --require-evaluation
aethel status
aethel log
aethel fsck

init resolves and records an immutable base revision. It downloads model metadata, not the base weights; training fetches the pinned weights. A local repository is discovered from the current directory or its parents. New commits use the configured author; without --author, initialization checks AETHEL_AUTHOR, USER, USERNAME, and LOGNAME.

train stages a new adapter in .aethel/workspace/. It starts from the pinned base rather than continuing from the previous adapter. Replacement is staged separately, preserving the old workspace on failure. Uncommitted workspace files require explicit --force replacement. A missing dataset is an error. --allow-stub deliberately uses synthetic data and records that fact; a stub run must not be presented as measured model quality.

commit snapshots the workspace and advances the current branch without changing the staged files. --require-evaluation makes failed held-out evaluation block the commit. Without it, evaluation failure or absence is recorded explicitly. Changing the staged artifacts invalidates previous evaluation hashes.

Keep split_seed fixed when comparing different training seeds. Normalized duplicate text is removed before splitting; contradictory labels are rejected. Each class needs enough unique examples for train, validation, and test partitions. Use validation data for development and select the test split explicitly for final reporting:

aethel eval main --split test --json

Evaluation requires the original dataset. A manifest records input hashes and split membership; changed data is refused. Datasets inside the repository are recorded relative to its root, while external dataset paths can remain absolute. Relocating a clone may therefore require restoring the original dataset at its recorded location.

Dataset identity, held-out splits, and comparable metrics

Training initializes a fresh adapter from the pinned base. Version-history parents describe snapshot lineage, not proof of training initialization from the parent adapter. Recorded metadata includes initialization, target modules, settings, model revision, environment, dataset identity, and whether synthetic data was used.

The stratified-unique-text-v1 manifest records raw input and canonical-example hashes, column names, label IDs, sample selection, split seed, and exact train/validation/test indices. Whitespace/case-normalized duplicate text is removed; conflicting labels fail. Each class needs at least three unique examples. seed controls training and split_seed controls data partitions, so repeated runs can vary initialization without changing the held-out comparison.

The dataset path is relative to the repository root when the file is inside it; external paths can be absolute. Evaluation reconstructs the recorded manifest and rejects altered inputs or split membership. Raw-byte and canonical-example hashes serve different purposes: formatting changes may preserve parsed examples while still changing the raw file hash.

Evaluation records accuracy, loss, macro-F1, support/confusion data, sample count, and hashes of the adapter, adapter config, and training metadata. A specification binds model revision, dataset/split identity, label meanings, token length, and sample count. Parent comparisons use one compatible specification; unrelated metric contexts cannot establish improvement. Loss is weighted by examples, including a final partial batch; macro-F1 includes configured classes. Non-finite model outputs fail explicitly.

Validation supports development; test results are explicitly requested for final reporting. Dataset manifests prevent accidental input drift, not dishonest input declarations or all semantic overlap between datasets. Reproduction still needs the original dataset, pinned base, and a compatible environment.

aethel diff main experiment --json

branch [name] [start-point] lists or creates branches. branch --delete <name> removes an inactive branch. Checkout accepts a branch, full commit hash, or unique short hash. Comparing the effective LoRA update

For supported standard LoRA, a layer update is:

Delta W = (alpha / rank) * B @ A

Comparing flattened factor vectors is misleading because rescaling A and inversely rescaling B leaves the effective update unchanged. The implementation compares effective updates in row blocks, reporting norms, distance, relative change, and cosine. Different ranks can represent the same update; zero updates have no defined cosine. Saved classifier/module tensors are reported separately. Unsupported PEFT variants and rank/alpha patterns are rejected rather than interpreted with the wrong formula. Comparison is descriptive, not an automatic merge.

Verified publishing and the remote fast-forward rule

  1. Walk every ancestor of the chosen tip locally and build the complete object plan.
  2. Ask the Hub which objects it lacks. The Hub checks hashes, so corruption is a miss.
  3. Send missing blobs, trees, bases, then commits in dependency order, preserving stored bytes.
  4. Publish the ref with the previously observed remote tip. The Hub revalidates all history, checks fast-forward ancestry and concurrency, appends accepted log entries, then saves the ref.

An accepted ancestor is not exempt from dependency validation on later publication. Display history limits do not shorten completeness checks. A repeated push reuses existing log entries. The log and ref are separate files: an append can succeed before ref persistence fails, leaving accepted entries without that branch pointing to them. Retry reuses those entries; this is not an atomic transaction across the entire Hub.

push --dry-run performs planning and negotiation without uploads or ref changes. Publishing a named branch is allowed even if another branch is checked out. The saved Hub repository name prevents a local folder rename from changing the published name. The write token authorizes the Hub request; it does not authenticate a commit's declared author.

Clone, pull, retries, and local work preservation

HubClient.repository captures one branch-tip snapshot. The raw route GET /api/v1/objects/{kind}/{object_hash} streams exact bytes with a digest header. JSON inspection routes remain useful for display but cannot reconstruct every original hash. HistoryDownload iteratively walks parents, validates commit shape, tree paths, every blob, the base, and the adapter/tree relationship. Received bytes land in unique temporary files, are size-bounded and hashed, and are installed only after matching the requested digest. Existing valid objects are reused; corrupt cached objects can be replaced by verified bytes.

Clone reserves a new destination exclusively and builds inside an owned temporary directory. After validating all published branches and a consistent pinned base, it restores the chosen tree and installs .aethel. It selects main, otherwise the only branch, otherwise requires an explicit branch. Failed cleanup removes owned temporary content and removes the destination only if empty. Concurrent unrelated files are preserved. Saved settings contain the Hub URL, repository name, and local author, not a token.

Pull captures the current attached branch and local tip, retrieves the corresponding remote history, and checks the pinned base. Equal tips or a locally ahead branch are no-ops. Divergence is refused. A fast-forward requires a clean workspace, stages the new tree, then installs with a ref-update callback that checks the captured HEAD/tip under the ref lock. Callback failure rolls back the workspace. Verified objects survive failed pulls for reuse. A remote growing after the initial snapshot is picked up on the next pull.

Retrieval bound Limit
Repository response 1 MiB
Structured object 16 MiB
Blob 64 MiB
Reachable object bytes 4 GiB, including cached objects
Restored workspace 4 GiB, counting repeated blobs once per filename
Objects / commits 100,000 / 10,000

These limits bound resource use during retrieval. The Hub's upload cap is separately configured and defaults to 64 MiB for both blobs and structured objects.

Using the remote workflow

Start the Hub in a separate terminal:

python -m hub

The default listener is 0.0.0.0:8000; browse http://127.0.0.1:8000. The default store is ./hub-data, relative to the server's working directory. Use AETHEL_HUB_DATA with an absolute path when launching it from different directories. Operations covers tokens and server configuration.

aethel push --repo sentiment --remote http://127.0.0.1:8000 --dry-run
aethel push --repo sentiment --remote http://127.0.0.1:8000
aethel clone sentiment teammate-copy --remote http://127.0.0.1:8000
cd teammate-copy
aethel fsck
aethel pull

On another machine, replace loopback with the shared Hub's reachable URL. Push validates local objects, uploads only what the Hub lacks, and moves the remote ref after complete validation. A repeated push reuses objects and accepted log entries. --branch can publish a named branch. The published repository name is saved in local configuration after success.

Clone downloads all published branches and their entire history into a new destination. It refuses existing directories, files, and symlinks, including empty directories. The default destination is the repository name. It restores main or the only branch; use --branch <name> if there is no unambiguous default or to select another branch. All history must use the same pinned base. --author chooses the identity for future local commits, not the authorship of received commits. The Hub must serve the raw-object endpoint introduced with clone/pull.

Clone saves hub_url and hub_repo, never a token. Later push/pull URL selection is: --remote, then AETHEL_HUB_URL, then the saved URL, then http://127.0.0.1:8000. Repository selection is --repo, then the saved name, then the directory name. --token or AETHEL_HUB_TOKEN supplies a shared Hub token when needed.

Pull updates only the current attached branch. It pins one remote snapshot, validates its history, and advances if the local tip is an ancestor. An already current or locally ahead branch leaves the workspace alone. Divergence, a missing remote branch, a base mismatch, or modified/deleted/untracked workspace files blocks replacement. --branch must match the current branch; checkout another branch before pulling it. There is no force-pull option. Interrupted transfers reuse verified objects on retry; a failed final ref update restores the old workspace.

Base weights and source datasets are not cloned. IPFS mirrors contain adapter blobs rather than complete repositories. Hash-verified retrieval and independent checkpoint verification are distinct operations; see Operations.

The append-only log and exact Merkle encoding

Accepted commit digests form an ordered, append-only log. The Merkle algorithm uses domain separation and promotes an odd last node unchanged:

leaf = SHA256(0x00 || UTF8(commit_digest_hex))
node = SHA256(0x01 || UTF8(left_digest_hex + right_digest_hex))

The UTF-8 hexadecimal encoding is part of this protocol. Distinct leaf/node tags prevent an internal node being reinterpreted as a leaf. Promotion avoids ambiguity caused by duplicating odd nodes. A proof supplies sibling digests and their sides; independent checkpoint verification also validates position and log size. Python and browser implementations have shared parity checks.

A complete inclusion proof, step by step

The verifier first hashes the expected commit as a leaf. At each level it concatenates the sibling and accumulated digest in the declared order, prefixes the node tag, and hashes again. An odd unpaired node advances without consuming a sibling. The computed final digest must equal the expected root.

A membership fold alone does not authenticate the root. Independent bundle verification also checks leaf position, log size, the exact prefix, and the checkpoint on the chosen chain. A proof for another position, with extra/missing steps, or against a substituted contract must not receive the same verdict.

Checkpoint contract and independent chain verification

The non-upgradeable contract records increasing (size, root, blockNumber, previousSize) checkpoints for one immutable log identity. Only the owner publishes; owner rotation requires nomination and acceptance. The contract checks ordering/ownership, not the correctness of the operator's data. A verifier reconstructs earlier prefixes to detect inconsistent history.

The worker validates accepted history before publication, persists signed transaction bytes and hash before broadcast, and records receipts after required confirmation depth. Retry reuses pending jobs and signed bytes. Independent verification checks the chosen chain ID, exact deployed bytecode, log ID, checkpoint, confirmation depth, positional inclusion, and all earlier checkpoint roots. Checks sample chain state and confirm the sampled block remains canonical; stale cached success is not proof of present confirmation.

A proof bundle can be saved and verified without the Hub, but chain verification still needs an independently chosen RPC/node. A self-consistent bundle from the Hub cannot choose its own trust anchor. Bundle verification supports up to 100,000 leaves and 1,024 checkpoints.

Deployed interface and invariants

The following is the complete contract source used to build the bundled runtime artifact.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.30;

/// @notice Immutable checkpoints for one named transparency log.
/// @dev Roots commit to history, not to model quality or honest training.
contract AethelCheckpoint {
    struct Checkpoint {
        bytes32 root;
        uint64 blockNumber;
        uint64 previousSize;
    }

    address public owner;
    address public pendingOwner;
    bytes32 public logId;
    uint64 public latestSize;
    mapping(uint64 => Checkpoint) public checkpoints;

    event Published(bytes32 indexed logId, uint64 indexed size, bytes32 root, uint64 previousSize);
    event OwnershipProposed(address indexed nextOwner);
    event OwnershipAccepted(address indexed newOwner);

    constructor(bytes32 id) {
        require(id != bytes32(0), "empty log id");
        owner = msg.sender;
        logId = id;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "owner only");
        _;
    }

    function publish(uint64 size, bytes32 root, uint64 expectedPreviousSize) external onlyOwner {
        require(size > latestSize, "size must increase");
        require(root != bytes32(0), "empty root");
        require(expectedPreviousSize == latestSize, "checkpoint changed");
        checkpoints[size] = Checkpoint(root, uint64(block.number), latestSize);
        latestSize = size;
        emit Published(logId, size, root, expectedPreviousSize);
    }

    function proposeOwner(address nextOwner) external onlyOwner {
        require(nextOwner != address(0), "empty owner");
        pendingOwner = nextOwner;
        emit OwnershipProposed(nextOwner);
    }

    function acceptOwnership() external {
        require(msg.sender == pendingOwner, "pending owner only");
        owner = pendingOwner;
        pendingOwner = address(0);
        emit OwnershipAccepted(owner);
    }
}

IPFS copies and integrity across transports

IPFS mirrors contain adapter blobs only. Pinning records the CID before gateway verification, so a failed download retries the same CID rather than creating another pin. Retrieval streams, enforces bounds, checks SHA-256, and preserves an existing different destination. Provider URLs are HTTPS except for allowed local development endpoints. Availability depends on the gateway and pinning account; a CID is not a complete repository backup.

An IPFS CID and Aethel's expected blob SHA-256 have different roles: the CID locates the pinned representation, while SHA-256 checks the exact adapter bytes expected by the commit. A successful pin does not prove future availability. The mirror job records the CID before gateway checking, so a timeout or HTTP 429 can be retried without another pin operation.

The Hub remains a source for complete repository objects. Adapter-only mirrors do not contain all commit/tree/base metadata or branch tips. Backups preserve those records separately.

This reference is taken from the same endpoint metadata used by the Hub's /api page. Expand a route for parameters, return values, and failure cases. Read routes are public. Publishing

POST /api/v1/repos/{repo_name}/negotiate · write token when configured

Ask which objects the Hub is missing.

Send the hashes the client holds; get back only the ones the Hub does not. This is what makes a push incremental, a second push of a branch that added one commit uploads one commit, not the whole history. Unknown object kinds and malformed hashes are dropped from the request rather than rejected, so a newer client talking to an older Hub degrades to uploading more than it needed to.

Returns: {repo, missing, branches}. missing lists requested objects; branches records the tips to check when publishing.

Parameter Location Required Meaning
repo_name path yes Repository name. Created on first ref update. 
{
  "have": {
    "commits": ["1b855137d2897c3e…", "335ac4c8aeeaad6d…"],
    "blobs":   ["2813bce55a21473b…"]
  }
}
PUT /api/v1/blobs/{blob_hash} · write token when configured

Upload adapter weights, addressed by their own hash.

The body is the raw file. No multipart, no filename field: content addressing means the hash in the URL is the name, so a filename would be a second identifier that has to be ignored anyway.

The Hub re-hashes what it receives and rejects a mismatch. A client therefore never has to trust that the Hub stored what was sent, and a truncated upload fails loudly instead of poisoning the store.

Returns: {hash, status, bytes}. status is stored or already-present, re-uploading a blob the Hub has is a no-op, not an error.

Parameter Location Required Meaning
blob_hash path yes SHA-256 of the bytes being sent, lower-case hex.
  • 413: Body exceeds AETHEL_HUB_MAX_BLOB (64 MiB by default).
  • 422: The received bytes do not hash to the digest in the URL.
PUT /api/v1/{kind}/{object_hash} · write token when configured

Upload a commit, tree, or base reference.

Same contract as a blob upload, for the three structured object kinds. The body is the object's canonical JSON, canonical because the hash is taken over those exact bytes, so re-serialising with different key order or spacing would produce a different digest and be rejected.

Returns: {hash, status}, with the same already-present shortcut.

Parameter Location Required Meaning
kind path yes One of commits, trees, bases.
object_hash path yes SHA-256 of the canonical JSON body.
  • 404: Unknown object kind.
  • 413: Body exceeds AETHEL_HUB_MAX_BLOB; enforced while reading.
POST /api/v1/repos/{repo_name}/refs · write token when configured

Advance a branch and append its history to the log.

The last step of a push, and the only one that changes what the Hub publishes. The ref moves only after every object reachable from the commit is present, so a published branch can never point at something a client cannot fetch.

Send expected_tip from negotiation, or null for a new branch, to reject a concurrent update. Updates must be fast-forward. A retry of the same published tip is accepted.

Ancestors are appended oldest-first, so log order matches commit order. The append is idempotent: re-pushing a branch adds only the genuinely new commits and leaves the root unchanged when there are none. That is why the response separates the two, logged_indices is where the whole history sits, appended_indices only what this call created.

Returns: {repo, branch, commit, logged_indices, appended_indices, log_size, root, branches}.

Parameter Location Required Meaning
repo_name path yes Repository name.
  • 409: A dependency is missing, the expected tip changed, or the update is not fast-forward.

The API's bundle is input to verification, not an authority for chain selection. Obtain the expected chain, contract, and log identity from an independent release record. Service layout

The deploy directory provides separate Hub and worker systemd units, a 15-minute worker timer, and a Caddy reverse-proxy configuration. They are templates for a Linux host; they have not been enabled on a remote machine in this workspace.

  • Install the checkout and virtual environment at /opt/aethel.
  • Create service users aethel and aethel-worker, sharing the aethel group.
  • Create /var/lib/aethel with shared group write access and the setgid bit. Existing mutable state files must also be group-writable; the Hub uses UMask=0007 for that shared state.
  • Store /etc/aethel/hub.env and /etc/aethel/worker.env as root-owned mode-0600 files. systemd reads these files before changing user. Keep the worker file out of the Hub's user permissions, checkout, image, and environment.
  • Configure DNS and AETHEL_PUBLIC_HOST for Caddy. The Hub stays on loopback behind HTTPS.
  • Install the units, start the Hub, then enable the worker timer after a manual cycle passes.
  • Alert on sustained /api/v1/health warnings or failures and worker service failures. A gateway failure must not be hidden by a healthy local object store.

Use a confirmation threshold appropriate to the deployment. Two confirmations are used for the documented testnet deployment; they are not a claim of irreversible finality. A changed or missing checkpoint loses its confirmed verdict on the next RPC check. Cached good results expire. Each chain verification rereads earlier checkpoints at its sampled block number and checks that the sampled tip remains canonical before reporting success. Historical confirmation records are not reused across probes, because a reorganization can replace previously confirmed blocks.

The worker currently uses the repository's explicit file-lock policy. A process killed while holding a lock can leave its lock file behind. Stop the worker, confirm the recorded process is no longer running, then remove only that stale lock before retrying. Use one signing worker per wallet. Other applications spending from the same account can consume a pending nonce. A reverted transaction or externally replaced nonce needs operator inspection; the worker does not silently choose another transaction or raise its gas price.

Questions the team should be able to answer

How is this different from storing adapters in Git or an artifact registry?

Git can store arbitrary files; artifact registries can store adapters and metadata. Aethel combines adapter/base relationships, held-out evaluation identity, effective LoRA comparison, verified retrieval, and an independently checkpointed accepted-history log in one workflow. This is a focused implementation, not a claim that other tools cannot support similar ideas.

Does a branch parent mean continued training from that adapter?

No. Training initializes from the pinned base. The parent records version-history succession. The explicit initialization record prevents those meanings from being confused.

Why keep both a tree and adapter_blob in the commit?

The tree restores the complete tracked workspace. The direct adapter reference lets mirrors and views locate weights without guessing a filename, and validation checks that both agree.

Does clone download the base and dataset?

No. It restores all published objects and branch history. The base model revision and dataset manifest tell the user which separate inputs evaluation needs. An external absolute dataset path may need restoring at its recorded location.

Why can pull refuse even after successfully downloading objects?

Downloading immutable verified objects is safe before deciding whether a local ref can move. A dirty workspace, divergent history, different base, or concurrent branch movement prevents installation. The old branch/workspace is preserved and the cached bytes remain for retry.

Can a successful browser proof check establish blockchain provenance?

A browser fold checks membership relative to the supplied root. Independent verification must also authenticate the expected chain, contract, and log identity, check confirmations, and reconstruct earlier prefixes. The Hub cannot provide its own independent trust anchor.

Does a checkpoint prove that the metrics or author are truthful?

It binds recorded claims and artifacts to a log prefix. It does not prove real-world identity, honest training, absence of harmful behavior, or useful model quality. Evaluation can be rerun with the required data/base/environment to inspect its claims.

Why are the test split and training seed separate from validation?

Validation guides development; an untouched test split supports final measurement. A separate split seed keeps examples fixed when training initialization changes. The recorded experiment reports validation only and does not claim an unseen test-set score.

What does a failed or stale external check mean?

The source may be unavailable or the previous observation may be too old. It does not silently become confirmed. A reorganization can change canonical-chain state; a gateway can rate-limit or lose availability while local content remains valid.

What survives an interruption?

Per-file writes are atomic; unfinished object writes do not publish refs. Staged replacement can preserve a workspace backup. Signed transactions and CIDs persist for retry. A killed process may leave locks or a partial log tail requiring inspection. Backups must include coherent object/ref/log/database state.

Does reading this replace the implementation?

This reference covers supported behavior, design, configuration, interfaces, validation, and recovery. Exact private helper behavior and third-party library internals remain in code. Run the documented workflow and recovery exercises to turn that knowledge into operational confidence; no documentation alone guarantees that every environment is correctly configured.

Object hashing/copying is linear in bytes processed. History validation visits reachable commits and dependencies; deduplicated objects are reused within an operation. Building the Merkle tree is linear in log length, while one membership proof has logarithmically many siblings. Independent verification also checks the supplied prefix and earlier checkpoints, so it does more work than a membership proof alone. These are algorithmic properties; no production throughput or latency bound is claimed.
