01
The idea

One frozen base, many small patches

Fine-tuning a language model with LoRA does not produce a new model. It produces a small set of low-rank matrices — a patch — that sits on top of a base model whose weights never change. That patch is around 0.6 MB. The base is around 250 MB.

Every existing tool versions the 250 MB. Aethel versions the 0.6 MB and stores the base by reference:

{
  "model_id": "distilbert-base-uncased",
  "revision":  "12040accade4e8a0f71eabdb258fecc2f7",   // immutable commit SHA
  "source":    "huggingface"
}

The revision is a Hugging Face commit SHA, never a tag. Tags move. A repo owner can retag main tomorrow and every "reproducible" pipeline pinned to it silently trains against different weights. A SHA cannot move — if the bytes change, the SHA changes, and resolution fails loudly instead of succeeding wrongly.

The consequence

A hundred experiments cost ~60 MB instead of ~25 GB, and a version's identity is a 64-character hex string that anyone can recompute from the bytes. That single property is what makes everything downstream — dedup, transparency logging, third-party verification — possible at all.

What you actually type

aethel init          # create .aethel/ (no database, no server)
aethel train         # LoRA fine-tune -> adapter in the workspace
aethel commit -m ..  # snapshot workspace -> content-addressed objects
aethel log           # walk history from refs through the store
aethel branch/checkout
aethel fsck          # re-hash every object, report corruption
aethel push          # upload to Hub, get a transparency-log receipt
02
Design premise

Why a chain and not a database

The first version of Aethel kept a SQLite file, repo.db, alongside the weights. It held commit rows, branch pointers and metrics. It was the fastest thing to build and it was the source of every serious defect in the audit.

The failure mode

A database next to the objects is a second source of truth. Once two places can disagree, one of them is lying and you cannot tell which. checkout.py could not resolve a commit without repo.db, which made the headline claim — "copy the folder and you have the version" — false.

The rebuild deleted SQLite entirely. History is walked from refs, through the object store, one parent_hash at a time. Three things fall out of that decision:

  1. Portability becomes true, not aspirational. .aethel/ is a directory of hash-named files. Copy it, zip it, rsync it — it works, because there is nothing else to bring.
  2. reindex became unnecessary. The plan specified a command to rebuild the cache from objects. With no cache, there is nothing to rebuild. A whole subsystem was deleted rather than written — the best kind of progress.
  3. Verification becomes possible for outsiders. You cannot hand someone a SQLite file and ask them to check your integrity claim. You can hand them a digest and a proof.

The cost is real and worth naming: reads walk the graph instead of hitting an index. For a history of hundreds of commits that is microseconds. For a history of millions it would not be, and the honest answer is that we would add a cache back — but as a derived cache that no read path is allowed to require.

04
Layer 1

The object store

Four kinds of object. Each is named by the SHA-256 of its own content, and each name is sharded on the first two hex characters so no directory ever accumulates tens of thousands of entries — the same trick Git uses.

.aethel/
├── objects/
│   ├── blobs/1b/b2d78c6d043feb…   raw bytes: weights, configs
│   ├── trees/8f/3a91c4…           manifest: filename -> blob hash
│   ├── commits/34/78ef8f…         commit metadata, keyed by COMMIT hash
│   └── bases/c0/1de9…             base-model reference objects
├── refs/heads/main                one line: a commit hash
└── HEAD                           ref: refs/heads/main

There is no index.db, no repo.db, no daemon and no lock daemon. The directory is the repository.

Three properties this buys

PropertyMechanismTest
Deduplication — identical weights are stored once, however many commits reference themblob key is the content hashtest_core_objects
Tamper evidence — a flipped byte anywhere is detectable without a reference copyfsck re-hashes every object and compares to its own nametest_s1_corruption
Portability — the folder is the whole repositoryno database; history walked from refstest_core_resolve

fsck, demonstrated

$ printf 'x' >> .aethel/objects/blobs/1b/b2d78c6d043feb…
$ aethel fsck
CORRUPT  blobs/1bb2d78c6d043feb1f72c4bb4b7294722bc7d3e7c87a0c57cb980c3797d513d3
         stored bytes hash to 9c4e2f…, not to their own name
1 corrupt object, 0 missing  (exit 1)

Nothing external was consulted. The name is the checksum, so corruption is self-announcing.

05
Defect S1.1

The bug that forced the rebuild

This is the most important slide in the deck, because it is the reason the project was rewritten rather than patched.

Version 1 stored commit metadata inside the adapter's folder: objects/<adapter_hash>/commit.json. Adapter hashes deduplicate by design. So two commits with byte-identical weights — say you commit, tweak the message, commit again — resolved to the same path. The second commit.json overwrote the first. Both commits still had rows in SQLite, so history looked intact.

Then checkout.py resolved commit_hash → adapter_hash → folder → commit.json. Checking out commit A returned B's message, author and parent. Silently. With exit code 0.

The transferable lesson

When a bug is possible, guard it. When a bug is representable, change the representation. Every guard is a line of code someone can delete; a layout that cannot express the bug survives careless maintenance.

06
Layer 0

Crash safety: no half-written state, ever

The audit found that the old commit() performed five mutating steps with no transaction, no fsync and no rollback. Kill it at the wrong microsecond and you get a repository that is neither the old state nor the new one.

Every write in Aethel now goes through aethel/core/atomic.py. Six steps, in this order, no exceptions:

Objects first, ref last

Atomicity per file is not enough — a commit writes several files. So the order is fixed such that every possible crash point leaves a valid repository:

Advisory locks

Two named locks per store — refs.lock/repos.lock for pointer moves, log.lock for transparency-log appends. Acquisition is os.open(path, O_CREAT | O_EXCL), which is atomic at the kernel level, with a timeout that raises LockTimeout rather than blocking forever.

A deliberate rough edge

Stale locks are not auto-cleared. If a process dies holding one, the next writer fails and a human deletes the file. That is Git's index.lock trade-off, chosen for the same reason: an automatic staleness heuristic ("older than 30 s must be dead") is wrong exactly when a machine is slow or swapping, and its failure mode is two concurrent writers — far worse than a confusing error message.

Canonical JSON

json.dumps(obj, sort_keys=True, separators=(",", ":"),
           ensure_ascii=False, allow_nan=False)

Hashing JSON only means anything if the same object always serialises to the same bytes. Sorted keys remove dict-order dependence; tight separators remove whitespace; allow_nan=False rejects NaN and Infinity, which are not JSON at all and which different parsers handle differently.

ensure_ascii=False is the load-bearing one. It makes the output match JavaScript's JSON.stringify byte for byte, which is what lets the browser verifier re-derive a digest we computed in Python. Emit é where JS emits é and every client-side check fails on any commit with a non-ASCII author name.

Walkthrough

The lifecycle, end to end

What train actually does — and its known warts

aethel/commands/train.py is the largest single command (477 lines): it loads a base model at a pinned revision, attaches a LoRA config via peft, runs a Hugging Face Trainer, and writes the adapter plus a training_info.json into the workspace.

Say this out loud in the demo rather than hoping nobody asks
  • The old code silently trained on f"sample training record {i}" when a dataset path was typo'd, and still produced a committable adapter with plausible metrics. That is fixed — it now hard-errors unless you pass --allow-stub — but the module docstring still describes the old fallback. Doc lag, not a live bug.
  • train.py bypasses aethel.core entirely: it hardcodes the literal string ".aethel" instead of using the repo resolver, and its TrainError sits outside the AethelError tree, so the shared handle_errors decorator does not catch it. It is the one module that has not been brought into the rebuilt architecture.
  • There is still no evaluation. The only recorded metrics are Trainer training loss and runtime. We cannot yet state whether any model we version is any good.
08
Layer 3

The push protocol

Four phases. The ordering rules are the same ones that make local commits crash-safe, applied across a network where the failure modes are worse.

Four trust properties

PropertyHow
Integrity end to endHash computed by the client before send, recomputed by the hub on write, echoed back, and re-compared by the client (_verify_echo). A byte flipped by a proxy is caught at three points.
No partial historyDependency-ordered upload plus ref-last means an interrupted push leaves orphans, never a ref into nothing.
IdempotenceRe-pushing the same commits resolves to the existing log leaves. The response distinguishes logged_indices (where they are) from appended_indices (what was new this time), so a retry after a timeout is safe and does not double-log.
The hub is untrustedClients verify the hub's claims rather than believing them. The hub also holds no outbound credential — no wallet key, no Pinata token — so even a fully compromised hub cannot forge an on-chain anchor.
09
Layer 4 · crypto

The transparency log

Every accepted commit becomes one leaf in a Merkle tree. The tree's root is a single 64-character digest that commits to the entire history of everything the hub has ever accepted. Change one leaf and the root changes.

{"index": 4, "commit_hash": "3478ef8f…", "repo": "demo/sentiment",
 "accepted_at": "2026-08-27T09:14:03Z"}

Leaves live in a JSONL file. The file is the truth and the tree is never cached — it is rebuilt from the JSONL on every read. That is slower and it is correct: a cached root is a second source of truth, and we already know how that story ends.

Domain separation, and why it is not optional

Odd nodes are promoted, not duplicated

When a level has an odd count, the last node rides up unchanged to the next level. The obvious alternative — duplicate it and hash it with itself — is the CVE-2012-2459 shape: it lets two different leaf counts produce the same root.

Append-only by construction

hub/log.py exposes read methods — entries, leaves, size, contains, tree, root, inclusion_proof, static verify — and exactly two that mutate: append and append_many. There is no update path and no delete path, so "append-only" is not a policy someone enforces; it is the absence of code.

One hub-wide tree, not one per repo

A tempting design gives each repository its own log. It is also a hole: an operator could drop an entire repository and no surviving root would notice, because that repo's root was the only thing committing to it. One tree over everything means deleting any repo breaks the single root that every receipt ever issued refers to.

The attack

The forgery domain separation prevents

This is worth demonstrating live, because it is the clearest possible answer to "why not just hash the children together and be done with it". The docstring of aethel/core/aggregator.py carries the working attack:

# with no 0x00 / 0x01 prefixes:
real   = MerkleTree([l0, l1, l2, l3])
forged = MerkleTree([H(l0+l1), H(l2+l3)])   # "leaves" are real's INTERNAL NODES

real.get_root() == forged.get_root()        # -> True

Verification

Inclusion proofs: self-contained by design

A receipt has to be checkable by someone who does not trust us and does not want to talk to us. So a proof carries everything the verifier needs and the verifier never calls back:

{
  "commit_hash": "3478ef8f5a49c54e1f89fb49fb21bb0c8f57f391b8f3a98e4108ce1722c2a207",
  "leaf_index":  4,
  "log_size":    8,
  "root":        "9fe876acfe73dd8e1a25dda156c533a1e15a4c4fe9416443c7def8776f0e60a0",
  "proof": [
    {"sibling": "c8a1e973…", "side": "right"},
    {"sibling": "4dc2e7aa…", "side": "right"},
    {"sibling": "4127e11d…", "side": "left"}
  ]
}

Three siblings for eight leaves — log₂(8). A million-entry log needs twenty. That logarithmic size is why this scales to a public registry and a database of "trust me" rows does not.

The fold, with real values

Below is an actual proof, generated by running aethel.core.aggregator on an 8-leaf log. Every digest is real; nothing here is a placeholder. Each rung takes the accumulator, folds in the sibling on the stated side, and hashes with the 0x01 node prefix.

Note the side field names where the sibling sits, so the verifier knows the concatenation order. Get it backwards and the fold produces a valid-looking digest that matches nothing — which is exactly the right failure: wrong order means wrong root, means rejected.

The one animation on this page

The ladder above staggers in at 70 ms per rung, in fold order. That is the project's own motion rule applied here: animate only where the sequence is the data dependency. Under prefers-reduced-motion: reduce the animation rule is not defined at all rather than being set to zero duration — a zeroed animation with backwards fill would still hold opacity: 0 through its delay, hiding content from the people who asked for less motion.

Five dashboard pages, no build step

No React, no Vite, no node_modules, no CDN. Jinja templates, one hand-written stylesheet (1,843 lines), inline SVG charts computed server-side, and self-hosted subset fonts. The reason is not minimalism for its own sake: a build step is a second artifact whose provenance nobody audits, on a project whose entire subject is provenance.

Content-Security-Policy

default-src 'none'; script-src 'nonce-<per-response>'; …

default-src 'none' means every asset class must be named explicitly — nothing loads by accident. The dashboard needs exactly two inline scripts, and the lazy fix ('unsafe-inline') would permit every other inline script too, including one an attacker injects. A nonce is minted per response and published on request.state.csp_nonce; it is never reused, because a fixed nonce is just unsafe-inline spelled with more characters. Alongside it: nosniff, and a Permissions-Policy that switches off geolocation, camera, microphone and payment.

The 359-line SHA-256 nobody wanted to write

Why not crypto.subtle.digest?

Because window.crypto.subtle is undefined outside a secure context, and the demo runs on http://192.168.x.x:8000 over the room's wifi. The browser API that exists precisely for this is unavailable exactly when we need it. So hub/static/verify.js implements SHA-256 by hand.

Hand-rolled crypto is normally a red flag, so it is fenced in: the file self-tests against published vectors on load — the empty string, "abc", and 55, 56 and 64 "a"s, chosen because 55/56 straddle the message-padding block boundary where naive implementations break — and if any vector fails, it refuses to render a verdict at all rather than showing a green tick it cannot justify. A separate CI script, scripts/check_verify_js.py, keeps the JS constants in lockstep with the Python.

Self-assessment

Roughly two and a half layers of five

If you count the six architectural layers, four are built. If you count them by weight — how much of the project's actual claim each one carries — the number is less flattering, and this is the framing to use with the panel before they use it on us.

What we say the project isHow much of it exists
"Version control for fine-tuned models"Done. Store, commits, branches, checkout, fsck, push. This is genuinely finished and genuinely correct.
"Crash-safe and tamper-evident"Done, and tested. The strongest part of the project.
"Publicly auditable"Done up to the hub boundary. The log is real, the proofs are real, the browser verifier is real. What is missing is the anchor — so today a hub operator could still rewrite history, and only the anchor closes that.
"An ML tool"Weakest claim. We can train and version an adapter. We cannot evaluate it, diff it, or merge it. A version control system for models that cannot tell you whether a model got better is doing half the job.
"Blockchain-backed"Paper only. A contract sketch, a store class with no callers, and a well-argued design. Zero deployed code.
How to present this without undercutting the work

The infrastructure is excellent and unusually rigorous for a capstone — 702 tests, a structurally-impossible-by-construction bug class, RFC-conformant crypto with a demonstrated attack in the docstring, a from-scratch SHA-256 with published-vector self-tests. Lead with that. Then name the two gaps yourself, in one sentence each: "evaluation is unwritten, and the anchor is designed but not deployed." Naming your own gaps is what makes the rest of the claims credible.

Layer 5

What the chain will — and will not — prove

Stating this precisely before building it, because the overclaim is the tempting one and a panel will reach for it immediately.

The anchor proves

will hold
  • A commit record existed at a given time
  • It has not been altered or removed since
  • — including by whoever runs the Hub

The anchor does not prove

gap
  • That the weights were really trained from the claimed base
  • That the data was what the record says
  • That the metrics were honestly measured

A liar can publish an honest-looking record. The anchor only stops them changing it afterwards.

Closing that second gap is what dataset fingerprinting, the reproducibility record and Ed25519 commit signing are for — and all three are unbuilt. Say so.

The contract, as designed

contract AethelAnchor {
    struct Batch { bytes32 root; uint64 logSize; uint64 timestamp; address submitter; }
    Batch[] private _batches;                 // append-only, one hub-wide stream
    mapping(bytes32 => bool) public rootSeen; // duplicate-root guard
    mapping(address => bool) public canAnchor;// allowlist

    event Anchored(
        uint256 indexed batchIndex,  // topic1 — ordering
        bytes32 indexed root,        // topic2 — reverse lookup: root -> tx
        uint64  indexed logSize,     // topic3 — which prefix of the log
        address submitter,
        uint64  timestamp
    );
    function anchor(bytes32 root, uint64 logSize) external;
}
DecisionReason
Exactly three indexed paramsEVM allows four topics and the event signature takes one. batchIndex, root and logSize are the three you would ever filter on.
No repoId fieldA leaf is not per-repo. The log is one hub-wide tree (§09), so a per-repo id on the anchor would imply a guarantee the structure does not give.
logSize must be monotonicA non-increasing logSize is not a mistake, it is a signature: it means the operator truncated the log. Making it checkable on-chain turns deletion into a visible event.
canAnchor allowlistNot optional. Without it, anyone can spam rows that render on our dashboard.
Append-only, no update or deleteSame principle as hub/log.py: the guarantee is the absence of a code path.
Etherscan-verified sourceUnverified, the events render as raw hex — unreadable on a projector, and unauditable by a panel member on their phone.
pending → confirmed statesSepolia reorgs are real. A UI that shows "anchored" the instant a transaction is broadcast is lying about finality.
The Hub holds no keyAnchoring runs as a separate job with the wallet credential. A fully compromised Hub still cannot forge an anchor — which is the entire point of anchoring a Hub you do not trust.

Prep

Questions you will get, and the honest answers

"Isn't this just Git with extra steps?"

Git stores whole files and has no notion of a base model, a training run, or a public log. The interesting parts here are the ones Git does not have: a base referenced by immutable revision SHA so reproducibility is checkable, and a Merkle transparency log so a stranger can verify history without trusting the server. The Git-shaped parts — content addressing, sharding, ref-last ordering — we copied deliberately, because they are correct and battle-tested.

"Why not DVC, MLflow, or Hugging Face Hub?"

They version artifacts by pointer and trust the server's metadata. None gives you a cryptographic receipt you can check offline, and none makes tampering by the registry operator detectable. That is the specific gap this fills. It is a narrow gap — say so.

"Why blockchain? Isn't that bolted on?"

It would be, if it were storing the models. It isn't — it stores one 32-byte root per batch. The honest framing: the Merkle log already prevents undetected tampering by the operator, because every issued receipt commits to a root. What it cannot do is stop the operator from serving a consistent alternate history to someone who has no old receipt. An external append-only timestamp closes that, and a public testnet is the cheapest one that a panel can independently check.

"You wrote your own SHA-256. Why should we trust it?"

You shouldn't, and it doesn't ask you to. It self-tests against published NIST vectors on every load — including 55, 56 and 64 byte inputs that straddle the padding boundary where naive implementations fail — and if any vector mismatches it refuses to display a verdict rather than showing a tick. It exists only because crypto.subtle is undefined on plain HTTP, which is what the demo runs on. On a deployed HTTPS hub the native API would be preferable.

"How do you know the S1.1 bug is really gone?"

There is no check to bypass. A commit's address is the hash of the commit's own bytes, so two commits that differ in any field — message included — land at different paths. Eight regression tests pin it, one of which asserts we didn't take the lazy fix of storing a full weights copy per commit.

"What happens if I Ctrl-C during a commit?"

You get unreferenced objects and an unchanged branch pointer — a valid repository in which the commit simply did not happen. Objects are written before the ref, and the ref move is a single os.replace. Cleanup is under except BaseException specifically so KeyboardInterrupt unlinks the temp file. Demonstrate it live; it is a good moment.

"Can it evaluate models?"

No. Not yet. It records training loss and runtime from the Hugging Face Trainer and nothing else. Eval split, accuracy and macro-F1 are the top open item, owned by Shravan. Don't dress this up.

"What's the biggest weakness?"

Two, and they are worth volunteering: the ML layer is thin — no eval, no diff, no merge — and the chain layer does not exist outside a design document. The infrastructure underneath both is finished and heavily tested, which is why those two are tractable rather than existential.
